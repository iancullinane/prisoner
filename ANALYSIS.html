Overview

prisoner is a portfolio/side project modeling the Prisoner's Dilemma. It is three things at once: a reusable Go library (pkg/prisoner) implementing the payoff matrix, a Cobra-based CLI (cmd/) for running games/simulations from the terminal, and an HTTP API (api/) plus a Vite/React frontend (web/) so humans can create players and record interactions against a shared backend. Storage is pluggable — in-memory, flat JSON file, or Postgres — selected via the --store flag / PRISONER_STORE env, all constructed behind a single openStores factory (cmd/store-opener.go).

API & Endpoints

The HTTP surface is a single *http.ServeMux (Go 1.22+ pattern routing) wrapped in a CORS middleware, constructed in api/server.go's NewPlayerServer.

MethodPathHandlerPurpose
GET/playerslistPlayersHandlerList all players
GET/players/{name}playersHandlerFetch a player by name
POST/players/{name}playersHandlerGet-or-create a player by name
GET/historyhistoryHandlerList all recorded interactions
GET/history/{id}historyHandlerFilter history by player UUID
POST/playplayHandlerPlay one round between two players, score it, record it

CORS middleware (withCORS)

Reflects whatever Origin header is sent back as Access-Control-Allow-Origin (rather than a hardcoded origin), so the Vite dev server or any future frontend origin works without configuration. Handles OPTIONS preflight with a 204 short-circuit before it reaches the mux. Covered by api/cors_test.go.

Request/response shapes

POST /play
{
  "playerA": "<uuid>", "playerB": "<uuid>",
  "playerAMove": "C", "playerBMove": "B"
}
→ 201 { "id": "<uuid>", "playerAScore": "S", "playerBScore": "T" }

Move and Result are single-rune enums (C/B, T/R/P/S) that marshal to/from single-character JSON strings (pkg/prisoner/prisoner.go) via a shared generic unmarshalRuneEnum.

Architecture & Dependencies

Layering

cmd/

Cobra commands: server, game, simulate, player, migrate. root.go wires Viper config resolution and a process-wide *slog.Logger. store-opener.go is the shared store factory used by every command.

api/

Thin HTTP layer: PlayerServer embeds http.Handler, depends only on the types.PlayerStore / types.HistoryStore interfaces — no knowledge of which backend is behind them.

internal/types/

Domain model: Player, Interaction, History, and the store interfaces every backend implements.

internal/store/{memory,file,postgres}/

Three interchangeable implementations of the same store interfaces.

pkg/prisoner/

Pure game logic — payoff matrix, move/result enums, Play(). No I/O, fully unit-testable, exported for external reuse.

prisonerdb/

sqlc-generated code from db/queries.sql against the goose migrations — gitignored, regenerated at build/Docker time.

web/

React + TS + Vite SPA; src/api/players.ts is the only fetch boundary, reading VITE_API_BASE_URL.

Configuration

  • --store / PRISONER_STORE: memory (default), file, or postgres
  • --log-level, --log-format: text or json, resolved once in PersistentPreRunE
  • DATABASE_URL: required only for the postgres store and for migrate
  • ~/.prisoner (yaml) or --config: optional Viper config file
  • VITE_API_BASE_URL: frontend's API origin (e.g. http://localhost:5001)

Migration safety model

The server process never runs migrations itself (documented deliberately in the README). migrate is a separate Cobra subcommand backed by embedded SQL (db/embed.go), invoked as a one-off task against the same container image — avoids concurrent DDL from multiple replicas and keeps the running server's DB role least-privilege.

Deployment & Platform Patterns

Beyond docker-compose for local dev, prisoner runs in production on AWS EKS, provisioned by a sibling AWS CDK repo (sheeta-games). The split is deliberate: the app repo stays lean and self-contained, while all Kubernetes manifests and cloud infrastructure live in sheeta-games. CDK owns the cluster and platform add-ons; application workloads are plain kubectl YAML applied by hand. This section documents the patterns that connect the two.

What the prisoner repo contributes to be "deployable"

  • Multi-arch images — the Dockerfile cross-compiles (GOOS/GOARCH=$TARGETOS/$TARGETARCH) and CI builds linux/amd64,linux/arm64 via buildx, because the nodes are arm64 Graviton (t4g).
  • A dependency-free /healthz — returns 200 without touching the DB; used for both k8s probes and the ALB target-group health check.
  • Embedded migrations — migrate up ships schema inside the binary (goose.SetBaseFS), so a migration Job needs no mounted files.
  • Runtime store selection — the same image runs memory or Postgres via --store, so the DB cutover is a manifest change, not a rebuild.
  • Same-origin SPA build — VITE_API_BASE_URL defaults empty, so the frontend calls relative /players, making the image environment- and domain-agnostic.

Container & image strategy

Backend image

Multi-stage Alpine, cross-compiled multi-arch. Built + pushed to ECR prisoner:latest by GitHub Actions via OIDC (no static keys).

Frontend image

Separate nginx image (prisoner-web) serving the Vite build with an SPA try_files fallback and its own /healthz. The backend stays API-only.

Moving tags

Both run :latest with imagePullPolicy: Always; a new build is rolled in via kubectl rollout restart.

CI cross-trigger guard

The two publish workflows use a runtime dorny/paths-filter gate so a web/**-only change doesn't rebuild the Go image (and vice-versa); tags/dispatch always build.

Platform provisioning (CDK, three stacks)

Foundation

VPC (public + private-with-egress), the Route53 hosted zone, and a wildcard *.adventurebrave.com ACM cert. Shared primitives, exposed as CDK refs.

Database

RDS Postgres (private, non-public), its credentials Secret, and the DB security group (bastion-only until wired to EKS).

Platform

The eks.Cluster (stable construct), an arm64 managed node group (AL2023), EKS access entries (not aws-auth), and every IRSA/Helm add-on below.

Platform consumes Foundation's vpc/hostedZone and Database's dbSecurityGroup/secret as cross-stack references — one-way (Platform → Database), which is what keeps cdk destroy PlatformStack unblocked during teardown.

IRSA + Helm controllers

One pattern applied three times: a Kubernetes ServiceAccount is bound to a narrowly-scoped IAM role via IRSA (OIDC AssumeRoleWithWebIdentity), then a Helm chart runs the controller Pod as that ServiceAccount so it inherits only the permissions it needs.

Ingress → ALB path routing (same-origin)

A single internet-facing ALB, built from one Ingress, fronts the whole app. Because the SPA and API share one hostname, there is no CORS and only one DNS record / cert to manage.

DNS & TLS

Stable hostname

ExternalDNS reads the Ingress host: and upserts prisoner.adventurebrave.com A/TXT records to the ALB — re-pointed automatically on every redeploy, so the URL survives new ALBs.

Wildcard cert, auto-discovered

The *.adventurebrave.com ACM cert (DNS-validated, in Foundation) is auto-discovered by the ALB controller from the Ingress host — no ARN in any manifest. Reusable by other apps, and it survives teardown.

HTTPS redirect

listen-ports [{HTTP:80},{HTTPS:443}] + ssl-redirect: '443' — plain HTTP is 301'd to TLS at the ALB.

  • Secret delivery — an ExternalSecret templates DATABASE_URL from the RDS secret's JSON into the prisoner-db k8s Secret; the credential is never baked into a manifest or image.
  • Migration — a run-to-completion Job (kept out of the bulk apply, run via make migrate) applies goose migrations before the app serves Postgres.

⚠️ Operational gotchas (learned the hard way)

  • Editing a manifest isn't deploying it — the Deployment must be kubectl apply'd, or the running Pod keeps its old spec (e.g. still --store memory while you think it's on Postgres).
  • Apply order matters on a fresh cluster — the namespace applies first, and the ALB/ESO admission webhooks must be ready before their objects, or apply fails with "connection refused calling webhook". make eks-up bakes in both waits.
  • Teardown order matters — make eks-down deletes the Ingress first so the ALB drains via its finalizer, then cdk destroy; the reverse can orphan ENIs and hang.
  • RDS is private — unreachable from a laptop; connect through the SSM bastion tunnel (and use host=127.0.0.1 so a local Docker Postgres on ::1 doesn't shadow it).

✅ Patterns worth reusing

  • Repo split — the app stays deployable-anywhere; infra + manifests live with the CDK that owns the cluster.
  • Same-origin routing — one ALB, one hostname, one cert; CORS eliminated by construction.
  • IRSA per controller — least-privilege, keyless AWS access for each add-on, scoped to exactly one zone/secret where possible.
  • Auto-discovered wildcard cert + ExternalDNS — no cross-stack cert wiring, and a stable hostname that survives cluster teardown/redeploy.
  • Migration as a deliberate one-off — decoupled from server startup, matching the app's existing "server never auto-migrates" design.

Technical Review

✅ Strengths

  • Clean interface boundaries — types.PlayerStore/types.HistoryStore let api/ and cmd/ stay backend-agnostic; three backends (memory, file, Postgres) implement the same contract and are swappable at runtime via one flag.
  • Pure, dependency-free game core — pkg/prisoner has no I/O and is exported independently, making the payoff logic trivially unit-testable (and reusable outside this repo).
  • Deliberate migration/deploy separation — explicit design choice (documented in README) to keep schema changes out of the server's hot path, appropriate for a managed DB like RDS.
  • Decent test surface for the size of the project — CORS behavior, HTTP handlers (via stub stores), and the Postgres store (via testcontainers, real DB not mocks) all have dedicated tests.
  • Structured logging with slog, component-scoped via logger.With(...), consistent from root.go down through stores.

⚠️ Concerns

  • In-memory store is not concurrency-safe (internal/store/memory/in-memory-store.go) — players/history slices are mutated with no mutex. The HTTP server can receive concurrent requests; two simultaneous POST /players/{name} or POST /play calls racing on the same store is a real data race (not just theoretical) whenever --store memory backs the server.
  • /play error handling swallows the real failure mode (api/server.go:88-97) — a "player not found" from GetPlayerByID returns 500 instead of 404, hiding a client error as a server error.
  • Repo root polluted with dev artifacts — player.db.json, history.db.json exist at repo root from local `file` store runs and aren't gitignored consistently; risk of accidentally committing local play data.
  • CORS reflects any Origin unconditionally — appropriate for a dev-only frontend, but if this server is ever exposed beyond localhost, reflecting an arbitrary Origin with no allowlist effectively disables the same-origin protection CORS is meant to provide (there's no credentialed-cookie use today, which limits the real-world impact, but it's worth an explicit allowlist before any public deploy).
  • No request size limits or timeouts on the HTTP server (cmd/server.go:36) — http.ListenAndServe with no ReadTimeout/WriteTimeout/MaxHeaderBytes is vulnerable to slow-loris-style resource exhaustion once this leaves localhost.
  • Frontend has a single happy-path component — PlayerManager.tsx covers list/create only; no UI yet for /play or /history, so the API's core gameplay loop isn't reachable from the web frontend yet.

💡 Recommendations

  • Add a sync.RWMutex to InMemoryPlayerStore/InMemoryHistoryStore, or document --store memory as single-connection/dev-only and default the server command to a safer store.
  • In playHandler, distinguish types.ErrPlayerNotFound from other errors and return 404 for it, matching the pattern already used in playersHandler's GET path.
  • Set explicit timeouts on the server (&http.Server{ReadHeaderTimeout: ..., WriteTimeout: ..., Handler: server}) instead of the bare http.ListenAndServe convenience wrapper.
  • Replace CORS origin reflection with an explicit allowlist (env-configurable) before any non-localhost deployment.
  • Extend the web frontend to cover /play and /history so the full game loop is playable end-to-end from the browser, matching the README's stated goal of "playing against real humans."
  • .gitignore the root-level *.db.json files unconditionally (currently only partially ignored per the working tree status).

Risk Assessment

LOW   for the CLI/library and Postgres-backed API path — well-tested, interface-driven, deliberate migration safety.

MEDIUM   for the HTTP server overall — the memory-store race condition and missing timeouts are real but only matter once this is running multi-connection or outside localhost, which is exactly the direction the project (web frontend, "play against real humans") is heading.
